# 技術轉唱歌／音樂 子品牌線：決策紀錄原始文字

> 本篇為 content-hub 主題頁 README.md 的原始討論脈絡存檔，供之後正式錄影時回頭核對決策過程用；非逐字對話紀錄，是整理後的重點摘要。

## 討論起點

content-hub 原本的內容飛輪：技術工作 → GitHub 紀錄 → YouTube 影片 → NotebookLM（單向，音訊再利用層）。

討論延伸出一個新的可能性：YouTube 之後，是否能「透過其他方式（唱歌、音樂）」再產生一輪內容，把技術素材改編成歌曲。

## 決策一：不跟現有技術系列放在一起

理由：

- 現有三個技術系列（`series/README.md` 記載的 DSOX4024G、AI機槽成長歷程、Claude Code 雲端開發）已經是成熟穩定的工作流，靠 `audio_transcribe` repo 的 profile 判斷機制運作，該機制依賴錄音檔名前綴比對
- 音樂改編是完全不同的創作動作（寫詞、選調、AI 作曲、後製），硬塞進同一套素材管理規則，容易被誤判成既有系列的新一集
- 品牌調性差異大：現有頻道定位是「SOP／自動化實戰」的專業教學，歌曲化內容偏娛樂／記憶點導向，兩者混在同一個位置會互相稀釋

## 決策二：整條線要物理拉出來，開全新獨立 repo

使用者原話重點：「技術工具，目前就很成熟的工作流了，所以不能放在一齊」「拉出獨立子品牌／播放清單做區隔（整條線要拉出來，不要放在同一個位置）」。

釐清後確認：

- 存放位置：全新獨立 GitHub repo（不是 content-hub 內的新頂層資料夾）
- 子品牌名稱：使用者尚未想好，暫時佔位，等想到正式名稱再回頭改資料夾名稱／README／repo 名稱
- 跟 `yt-auto-publish` 分工模式的差異：`yt-auto-publish` 拉出獨立 repo 是「保密到公開那一刻」的安全考量（未公開 video_id 不能寫進公開 repo）；這次拉出獨立 repo 是「品牌區隔」考量，不是保密需求，兩者外殼相似（獨立 repo＋content-hub 留規劃紀錄互相參照）但背後原因不同

## 待使用者拍板的事項

1. 子品牌正式名稱
2. 新 repo 命名與 Public／Private 屬性（初步判斷不涉及未公開內容，傾向 Public，待使用者最終決定）
3. YouTube 通路：沿用既有頻道另開播放清單，或開全新頻道
4. AI 作曲工具選型（Suno／Udio／其他）與商用授權、YouTube Content ID 版權風險
5. 第一支 pilot 內容的選定（建議挑一支已發布的技術影片改編，成本最低）
