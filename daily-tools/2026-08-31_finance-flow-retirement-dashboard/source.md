# Finance Flow — 在既有的個人記帳單檔 App 上，長出一個「退休存量儀表板」

> 來源路徑：`退休財務作戰系統/`（`finance-flow-albert-v4.html`，規格書 `README.md` v1.0，2026-02-10）
> 設計者：Albert.Chou　最後更新：2026-06-08（資料夾同步時間）

---

## 這是什麼

一支單一 HTML 檔、純 LocalStorage 離線運作的個人記帳工具，這次新增的不是記帳功能本身，而是一個「退休儀表板」模組：在既有的「Flow（現金流：收入/支出/轉帳）」記帳邏輯之上，補上「Stock（資產負債表）」跟「Rules（底線與提存規則）」兩層，把「退休金夠不夠撐多久」變成六個可以一眼判讀的 KPI，而不是一堆散落的 Excel 分頁。

## 為什麼值得關注

多數人管理退休金的方式是「記帳 App 管流水帳、Excel 管資產、腦袋記提存率」，三個東西互不相通，也沒有一個地方能回答「如果現在退休，手上的錢能撐幾個月」。這支工具的做法值得注意的地方在於它是**先寫規格書再動工**：README.md 開頭就明確定義「不動既有功能」的邊界（`tx` 交易邏輯、大額門檻、多幣別、類別管理、匯出格式全部維持不變，只新增 `state.retirement` 這個獨立欄位），這是一種對「單檔案、零依賴」架構刻意剋制的擴充紀律——避免功能疊加久了變成誰都不敢碰的意大利麵。同時它把「退休規劃」拆解成可執行的具體指標（Runway、Income Coverage、Emergency Fund Gap），而不是含糊的「存夠退休金」，這個拆解角度本身就是可以獨立拿出來講的財務規劃方法論。

## 技術重點（實際看過程式碼）

- **Runway／Coverage／Gap 三個核心 KPI 都是純函式即時算出**：`calcRetirementKpis()`（finance-flow-albert-v4.html:1708）每次都從 `assets`／`liabilities`／`incomeStreams` 原始陣列重新加總，不做快取。`runway = liquidTWD / floorTWD`（流動資產可以撐幾個月）、`coverage = streamTWD / floorTWD`（股息/債息/租金等被動收入能覆蓋日常底線支出的比例）、`gap = emergencyFundTarget − liquidTWD`（緊急預備金還差多少），三個指標共用同一個「floor（底線支出）」分母，任何一筆資產或支出異動都會立刻反映到儀表板，不需要手動重算。
- **底線支出的自動估算刻意設計成保守值**：`calcFloorAuto12mTwd()`（:1681）只認定 `固定支出`／`保險`／`稅務`／`交通` 四個類別為「必要支出」，抓過去 12 個月、僅限 TWD 幣別的支出加總後，**固定除以 12**——即使使用者只有 3 個月的記帳資料，分母也不會跟著縮小成 3。程式碼裡直接寫註解說明這是刻意選擇：「避免資料不足時，平均值算出來過度樂觀」。這是一個「寧可低估、不要高估」的保守估計設計取捨，在財務類工具裡是值得注意的細節。
- **多幣別換算是手動維護表，不接外部匯率 API**：`fxToTwd()`（:1624）查一張使用者自己填的 `fxRates` 表（幣別、換算成 TWD 的匯率、更新日期 `asOf`），查不到就直接回傳 0（不是報錯，是靜默歸零）。README 的 Roadmap 明確把「匯率自動化」列為之後才做的項目，v1 階段刻意用最簡單的靜態表換取零依賴、離線可用。
- **跨裝置同步靠「複製貼上 JSON」，不是雲端也不是檔案**：`mergeRetirement()`（:2043）用 Map by id 做合併，晚匯入的資料覆蓋舊資料（last-write-wins），`fxRates` 則是用幣別代碼當 key 合併。UI 分成兩種同步範圍——只同步 retirement 模組、或連交易紀錄一起同步（`importJSON()`，:2076 會判斷 payload 裡有沒有 `data.state` 來分流兩種合併路徑）。整個「多裝置同步」機制完全靠一個 textarea + Validate + Apply 按鈕完成，沒有後端、沒有帳號系統，是一個很精簡的 offline-first 合併範例。
- **版本號其實有點分裂**：檔名是 `v4`，README 規格書標題卻寫著針對 `v2` 的 Add-on，HTML 內部的 `<title>` 跟 `STORAGE_KEY`（`"albert.finance.v2"`）也都還停在 `v2`，`state.version` 也是數字 `2`。三者對不上代表這支工具走的是「持續在同一份規格上疊加」而非「每版重新定版號」的開發習慣——檔名的 v4 反映的是檔案本身第幾次另存,不是資料結構版本號。

## 可延伸應用角度

- **Runway / Income Coverage / Emergency Fund Gap 這三個財務指標本身**很適合拆成一支獨立的觀念影片，跟工具實作解耦——這是可以套用在任何人身上的「退休準備量化框架」，不需要用這支特定工具也能講清楚。
- **「先寫不破壞既有功能的規格書、再動工」**這個開發習慣，適合放進之前累積的「Albert Style 工具箱」系列裡，跟已介紹過的 `NVQual`、`SIT Storage Stress Toolkit`（`daily-tools/2026-08-18_nvqual-usb-blacklist`、`2026-08-19_sit-storage-stress-toolkit`）一起講「同一位設計者、同一套工程紀律」的共通脈絡，只是這次場景從硬體驗證換成個人理財。
- **靠複製貼上 JSON 做離線多裝置合併**的做法，可以獨立做一支「不架後端也能同步資料」的技術短片，用這裡的 last-write-wins by id 當具體案例，講清楚它跟真正的 CRDT／雲端同步差在哪裡、什麼情境下這種簡化做法就夠用。
- 保守估算底線支出（資料不足時故意不虛高平均值）這個細節，也適合當作「財務試算工具設計時該注意的偏誤方向」案例，跟本週稍早介紹的硬體驗證工具裡「寧可誤判需要人工複查、也不要漏判」的保守設計邏輯（見 `SIT Storage Stress Toolkit` 的 `UNVERIFIED_NARROW` 判定）互相呼應，可以做成一集講「不同領域工具，同一種風險趨避設計哲學」。
