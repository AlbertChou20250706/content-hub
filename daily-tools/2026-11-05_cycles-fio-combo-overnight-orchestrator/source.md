Cycles_FIO_Combo 是把 Albert 兩套已經各自驗證過的工具——電源循環測試框架 `Auto_Test_v7`（Reboot/Shutdown/DC/AC）與儲存裸碟壓力測試工具 FIO（`Storage_Stress_AlbertStyle_Linux.sh` v9.21.0）——串成「一份計畫檔、一支腳本」的長時間無人值守協調引擎。過去這兩套工具要人工切換、人工看結果；現在寫一份 `.plan` 計畫檔，`combo_run.sh` 就能照順序跑完電源循環與儲存壓測,過夜或連續數天不需要人在旁邊看,每個階段自動判定 PASS/WARN/FAIL。

> 來源路徑：`Cycles_FIO_Combo/`（README.md v1.3.4，2026-11-04 首次真機驗證）。已發布過的《SIT 電源循環回歸測試框架》（2026-10-06）與《SIT Storage All-Stress Toolkit》系列（2026-08-19、2026-10-10）分別介紹了 `Auto_Test_v7` 與 FIO 工具本體；這篇只聚焦在這兩套工具「怎麼被串起來」的協調層,不重複介紹底層引擎。

## 為什麼值得關注

電源事件後「碟少了一顆」或「PCIe 掉速」這類問題,常常因為沒人在測試中途盯著,直到下一次要用才被發現；而真正會讓人長時間離開現場的情境（過夜、連續多天）,恰好就是最需要有東西在背後持續比對硬體狀態的時候。這套工具的核心價值不是重寫電源測試或儲存壓測的邏輯,而是在**不碰內層任何一行程式**的前提下,補上「誰來協調兩套獨立工具」「每個階段後怎麼自動判斷有沒有異常」「SUT 掛掉了要不要自己救回來」這三個原本要靠人工填補的空隙。README 也罕見地在最上面用警語清楚寫明「目前只在真機跑過一次煙霧測試,AC/DC/Shutdown、過夜與雙碟以上尚未在真機驗證」,把模擬環境覆蓋與真機驗證的邊界切得很乾淨。

## 技術重點

實際下載整個資料夾（`combo_run.sh` 2029 行、`combo_report.sh`、`config/`、`docs/`、`samples/` 等）並讀過 README 全文與腳本後,幾個值得拆解的設計：

- **協調層與執行層徹底分離**：`Auto_Test_v7/` 與 `fio/` 都是「原封不動的複本」，`combo_run.sh` 只在外層呼叫 `Auto_Test_v7/run_test.sh -y -t <類型> -c <圈數>` 和 SSH 部署 FIO 腳本到 SUT 背景執行、輪詢取回成果,刻意不讓兩邊程式碼分岔，升級時直接整個資料夾覆蓋即可。
- **FIO 清空 SEL/dmesg 前先搶一份證據**：FIO 工具開跑時會做 `pretest_cleanup` 清掉 BMC SEL 與 dmesg，這會把電源階段留下的異常紀錄一起洗掉。`combo_run.sh:942` 的 `collect_evidence()` 在呼叫 FIO 之前先把 `ipmi_cmd sel elist` 存成 `evidence/sel_before.txt`，確保跨階段的故障證據不會被下一階段的前處理動作消音。
- **硬體指紋比對踩過的真實坑直接寫進版本歷史**：v1.1.0～v1.3.4 全部標註同一天（2026-11-04），是首次真機煙霧測試後的連續修正——`sut_fingerprint_raw()`／`sut_fingerprint()`（約 573-607 行）原本把 BMC 的 USB 虛擬裝置（開機後才出現的虛擬媒體 `Virtual HDisk`、USB 虛擬網卡）也算進硬體指紋，導致 Reboot 階段必定誤判 FAIL；v1.2.1 改成只算實體網卡、排除 USB 傳輸與 0B 容量的碟，並新增 `HW_IGNORE`（`combo_run.sh:597` 用正規表示式套用）讓現場其他「忽有忽無」的裝置也能自行排除。
- **身分防呆是從「設定填反」的真實案例反推出來的**：`IDENTITY_GUARD`（`combo_run.sh:96, 1342, 1410-1413`）會比對 BMC FRU 序號與 SUT DMI 序號，序號對不上就代表 `client.conf` 與 `ipmi.conf` 指到了不同機器（電源操作打 A 機、FIO 卻跑在 B 機），預設直接擋下；`--pin-target` 再把確認過的目標序號寫進 `config/target.pin`（`combo_run.sh:53`），之後資料夾被誤複製、設定指到別台時，前置檢查會直接擋下。v1.3.4 更進一步偵測「SUT 與 BMC 位址填反」——起因是 `--init-config` 精靈的預設值被整排按 Enter 沿用，剛好把兩個 IP 填反。
- **誠實分級的驗證狀態**：README 把「真機驗證」（僅 `fio_smoke.plan` 全唯讀流程，2026-11-04 首跑）與「模擬環境驗證」（用假的 ssh/ipmitool/lsblk/dmesg 模擬介面與結束碼，覆蓋故障注入、SUT 失聯恢復、`--bg`/`--resume`/`--abort` 等控制流程）分開列表，並列出建議的實機驗證順序（煙霧測試 → 加 DC/Shutdown → 加 AC → 短時間破壞性 FIO → 過夜）。這種先把「測過的」「模擬測的」「完全沒測的」三層邊界畫清楚，再給出驗證路線圖的寫法，比直接宣稱「已完整測試」更可信。

## 可延伸應用角度

- 可以跟已發布的《SIT 電源循環回歸測試框架》《SIT Storage All-Stress Toolkit》系列做成三部曲：兩支各自獨立驗證過的工具 → 這篇的協調引擎，示範「不碰內層程式碼、只在外層補協調與防呆」的整合思路，對比「重寫一套大工具」的常見做法。
- v1.1.0→v1.3.4 在同一天內因為一次真機煙霧測試就連續修了 5 個版本（USB 虛擬裝置誤判、身分防呆、位址填反偵測），適合做成一支「真機驗證為什麼比模擬環境更重要」的案例短片，逐條對照版本歷史裡「實機案例」的描述。
