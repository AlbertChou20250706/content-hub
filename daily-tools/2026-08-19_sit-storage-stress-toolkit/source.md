# SIT Storage All-Stress Toolkit — 把「PCIe 降級」誤報和「熱誤判」從硬體驗證流程裡拆掉

> 來源路徑：`Sustain/FIO_Test/For_RedHat/v9.14.0/`（`Storage_Stress_AlbertStyle_Linux.sh` v9.14.0，文件同步至 v9.11.0）
> 設計者：Albert Chou　最後更新：2026-08-18

---

## 這是什麼

一支單一檔案的 Bash 腳本，對 NVMe / SATA 裸碟（raw block device，`--direct=1`，繞過 page cache）施加 fio 壓力測試，同時做三件事：判定 `lspci` 回報的「PCIe 降級」是不是真降級、用 SMART + BMC 雙資料源即時監看溫度、把結果整理成一份可摺疊的 HTML 報表。自 v9.7.1 起改成「一支腳本涵蓋所有支援發行版」（RHEL/Rocky/Alma 8·9·10、Ubuntu、Debian、SLES、Arch），不再需要為不同 distro 維護分岔版本。

## 為什麼值得關注

這支工具解決的是硬體驗證裡兩類「明明沒壞卻被誤判成壞」的老問題，而且都有具體的根因分析，不是憑空加規則：

- **PCIe「降級」假警報**：`lspci -vv` 顯示 `Speed 16GT/s, Width x2 (downgraded)` 時，多數人直覺判定是硬體故障。但 `lspci` 只比對 Endpoint 自己的 LnkCap 跟目前的 LnkSta，**從不回頭查上游 Root Port 實際能供給幾條 lane**。如果主機板本來就把某個插槽設計成 x2（把 lane 分給 OCP NIC 之類），SSD 標稱 x4、實跑 x2 是兩端能力取交集的正常結果，根本不是故障——但 `lspci` 的原生輸出完全沒有能力分辨這兩種情況。
- **溫度單位誤讀導致的假過熱**：部分環境（實測見於 RHEL 10 + nvme-cli 2.11）的 `nvme smart-log` 只輸出華氏加克氏、不含攝氏。舊版解析邏輯「抓第一個數字」，把 `149°F` 誤當成 `149°C`，報表顯示碟溫飆到 149 度，但 BMC 板端量到的真實溫度只有 65°C。這種 bug 一旦上線，會讓一批本來合格的碟被錯殺。

這兩類問題的共通點是：現有工具鏈（`lspci`、`nvme-cli`）給出的原始數字本身沒錯，錯的是「不假思索直接採信」的解讀方式。這正是伺服器硬體驗證裡最容易被輕忽、卻最常造成誤判的一類坑。

## 技術重點（實際看過程式碼）

- **PCIe 判定邏輯**：實效頻寬上限 = min(Endpoint LnkCap, 上游 Root Port LnkCap)，拿這個值跟實際協商到的 LnkSta 比對，分成四種判定：`OPTIMAL`（跑滿上限）、`BY_DESIGN`（跑滿上游上限但低於 Endpoint 標稱——判 PASS，不是故障）、`TRUE_DOWNGRADE`（低於兩端共同上限——真故障）、`UNVERIFIED_NARROW`（上游讀到無效值，常見於 AMD 平台未啟用的 port，需人工確認）。BDF 路徑解析還做了四層 fallback（`/sys/block/<drv>` → `.../device` → `.../device/device` → `/sys/class/nvme/<controller>/device`），應付特殊控制器或 NVMe-oF 拓撲下符號連結不含 PCI BDF 的狀況。
- **溫度解析改用克氏優先**：既然克氏值在 `nvme-cli` 各版本輸出中一定存在（不管有沒有印攝氏/華氏），修法是一律以 `C = K − 273` 換算，不再猜測「第一個數字是哪個單位」。同時加了一道防呆：即使解析正確，若峰值溫度仍超過 100°C（NVMe 物理上不可能），報表會標記 WARN 並提示對照 BMC 板端數值——只有 BMC 也同步異常才是真事件，否則多半是解析問題。
- **BMC 感測器身分對應是個沒有直接答案的問題**：IPMI 感測器名稱（如 `M.2_NVMe_2_T`）跟 Linux 裝置名（`nvme1n1`）之間沒有系統性對應資訊。腳本提供的 `--auto-map` 做法很值得拆解：把每顆碟的 SMART 溫度（已知身分）與所有 BMC 感測器溫度（未知身分）做「去趨勢相關分析」——先扣掉「全體平均溫度」這個共同上升的成分，只留下每顆碟自己的微觀波動當指紋，曲線形狀最吻合的就判定是同一顆裝置，全程零額外測試時間。備援手段 `--calibrate-sensors` 則是從早期「逐顆單獨施壓」（8 碟需 53 分鐘、只認出 2/8）改成「全部並行 + 交錯延遲啟動」，靠「誰先開始升溫」而非「誰升溫最多」判斷，8 碟耗時降到 ~10 分鐘、認出 5–8/8；寫入負載的訊號強度（+14~27°C）遠勝讀取負載（+1~3°C）。
- **README 文件其實跟不上腳本本身**：文件開頭老實寫明「內容同步到 v9.11.0，v9.12.0–v9.14.0 新增功能尚未寫入」。實際翻程式碼會發現 `--spec-verify`（Layer 3 規格書比對模式，v9.13.0–9.13.1 加入）已經做出來了：跑固定的 Seq R/W、Rand R/W 四項負載去對齊原廠規格書量測條件，並且在 HTML 報表新增 Section 2c——這正好補上文件裡自己承認「Layer 3 比對邏輯尚未串接」的那個缺口，是一個「翻程式碼才抓得到文件已經落後於實作」的具體例子。
- **自我基準回歸（Layer 2，v9.11.0）**：`--set-baseline` 在已知良品碟上跑一次，存成 `baseline_<型號>.conf`，之後同型號每次測試自動比對 `CONSISTENT`（±10% 內）/ `REGRESSION`（退步）/ `ANOMALY_HIGH`（超出 +15%，多半是測試條件變了而非真變快）。這一層刻意不依賴任何外部規格書，抓的是「同一批碟前後不一致」「韌體更新後劣化」這類規格書比對本來就抓不到的問題。

## 可延伸應用角度

- **PCIe「降級」誤報**這個主題本身就適合單獨拉出來做一集：`lspci` 顯示 downgraded 不等於故障，硬體測試工程師很容易被原生工具的字面訊息誤導，這是一個具體、可演示、又通用（不限這支腳本）的硬體驗證知識點。
- **溫度單位誤讀（149°F 被當成 149°C）**是很好的「一行解析邏輯決定測試結果對錯」案例，可以做成「debug 案例研究」類型的短片，強調雙資料源交叉驗證（SMART vs BMC）的價值。
- **`--auto-map` 的去趨勢相關分析**演算法本身值得拆解成一支「巧妙工程技巧」影片：如何用時間序列相關性、在零額外測試時間的前提下，解決一個 IPMI 天生沒有答案的裝置身分對應問題。
- 這支工具在輸出資料夾結構（`reports/logs/json/csv/debug`）上刻意向上週介紹過的 `NVQual USB Controller Blacklist Helper`（`daily-tools/2026-08-18_nvqual-usb-blacklist`）對齊，README 裡甚至附了逐項對照表。兩支工具都出自同一位設計者、同一套「SIT 硬體驗證工具鏈」思路，適合串成一個「Albert Style 硬體驗證工具箱」系列，講設計哲學上的共通點（單一腳本零依賴、結構化多格式輸出、真實性驗證不信任 exit code）。
- **離線 air-gapped 安裝**（`--iso`，把 RHEL 安裝 DVD 掛成本機 repo）解決的是產線 SIT 機無法連外網、無訂閱的真實場景，也可以獨立成一則「無網路環境怎麼幫伺服器裝測試工具」的實用小技巧內容。
