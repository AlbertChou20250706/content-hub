OOB_Check 是一支透過 IPMI（ipmitool + lanplus）從 BMC 帶外（Out-of-Band）掃描 RX4770 M7/M8 伺服器 Combo 背板 FRU EEPROM 的 PowerShell 工具，用來確認每個 Combo 背板是否真的被系統偵測到。

## 為什麼值得關注

Combo 背板這種擴充模組，裝錯、沒插好或 EEPROM 故障時，從作業系統內部很難直接判斷「硬體到底有沒有被認出來」，傳統做法常常要開殼、目視、或登入 BMC Web UI 一個個位址點開確認，效率低也容易漏看。OOB_Check 把這個檢查流程做成一支腳本：帶外連線、讀主機板 Field2 辨識機型配置、只掃該配置該有的 FRU 位址，整支流程不需要進系統、不需要停機,對 SIT 測試或出貨前驗證都是很實際的時間節省。

資料夾裡的 README 也誠實記錄了這支腳本「現在的真實狀態」——這點本身就值得拿出來講：2026-09-24 修了三個會讓腳本完全跑不起來的 bug（遺漏的右括號、未初始化的雜湊表、游離字元），第四個已知問題（`ConvertFrom-SecureString -AsPlainText` 僅 PowerShell 7 支援）則還沒修,README 直接寫明「尚未在實機 BMC 上執行過」。這種「修好語法錯誤 ≠ 驗證過實際行為」的區分,是看別人工具、也是看自己工具時很該養成的習慣。

## 技術重點

實際讀過 `OOB_Check_v2.3.ps1` 與 README 後，幾個值得注意的設計：

- **用 Field2 動態決定掃描範圍，而不是無差別全掃**：腳本先對位址 `0x00` 執行 `fru print`,從回應裡用正規表示式抓出 `Field2`（格式類似 `VR\d+f;VDFf;...`),再去 `combo_map.csv` 查表,對到就只掃該機型配置應有的 Combo 位址（`0xB0`/`0xB2`/`0xB4`/`0xB6`/`0xB8`/`0xBA`,分別對應 Combo 0-3 到 20-23）;查不到才退回全掃六個位址,並印警告。這個設計把「盡量少打 IPMI 指令」跟「查無資料仍要保底全掃」兩個互相拉扯的需求一次處理掉。
- **位址掃描是三層迴圈的窮舉**：對每個預期位址,依序試 I²C bus `0,1,2,3,4,6,7`,每個 bus 再試五種 bridge target（無指定、`-t 0x12`、`0x14`、`0x16`、`0x18`),只要其中一次 `fru print <addr> -b <bus> <target>` 執行成功（`$LASTEXITCODE -eq 0`)就記 `PASS` 並跳出,全部組合都失敗才記 `WARN ... EEPROM not present`。這種「找到就停、全部試過才算失敗」的短路邏輯,是這類硬體探測腳本常見也值得學的模式。
- **一個隱藏的真實 bug，README 誠實揭露但程式碼還沒清掉**：第 66 行跟第 95 行各有一次 `Read-Host -AsSecureString "Enter Password"`,第一次讀到的密碼完全沒被使用,第二次輸入的才真正參與後面的 `ipmitool` 呼叫——使用者會被要求打兩次密碼,README 直接把這個現象寫成「已知注意事項」而不是藏起來,對照程式碼可以清楚看到第 76 行賦值的 `$BmcPass` 在第 95 行又被整個覆蓋掉。
- **密碼輸入本身做得比旁邊的手動測試批次檔安全**：主程式全程用 `SecureString` 互動輸入密碼,帳密不落地、不寫死;但同資料夾另外附的幾支手動測試用 `.bat`（`fru_list.bat`、`single_test.bat` 等）是直接把 BMC IP、帳號、密碼寫死在檔案裡方便手動跑測試,README 也特別用安全提醒標出來,交代「請勿原樣分享,請改成自己的 BMC 資訊」——這份內容只聚焦在設計良好的主程式,不會也不該把那些寫死密碼的輔助批次檔內容搬出來。
- **跨 PowerShell 版本相容性是另一條暗線**：README 記錄腳本檔案被加上 UTF-8 BOM,是因為原檔含中文卻沒有 BOM,在 Windows PowerShell 5.1 下會把中文字串解析壞;而 `ConvertFrom-SecureString -AsPlainText` 只在 PowerShell 7+ 支援,5.1 環境要改用 BSTR 轉換這種比較底層的寫法——這些都是寫跨版本相容的 PowerShell 工具時容易踩、但很少被寫進文件的細節。

## 可延伸應用角度

- 適合做成「讀別人程式碼時怎麼分辨『修好語法』跟『驗證過行為』」的案例:這支腳本語法檢查 0 錯誤,但 README 自己承認沒在實機測過,可以用來講「能執行」跟「邏輯正確」是兩件事。
- Field2 比對表 + 查不到就全掃的設計,適合拉出來講「參數化設定檔 vs. 寫死邏輯」這類取捨——同樣的模式在很多硬體相容性腳本（例如比對機型、韌體版本）都用得到。
- 兩次密碼輸入的 bug 加上「主程式用 SecureString、旁邊批次檔寫死密碼」的對比,可以做成一段「密碼要怎麼安全地在腳本間傳遞」的小科普,對照這兩種不同做法的風險差異。
