# 技術架構圖_模組清單 — 伺服器健康監控儀表板的技術架構藍圖

這份文件是一張完整的系統架構規劃圖，目標是把「讀 BMC 感測器資料」這件事，從一堆各自獨立的腳本，收斂成一套可以長期維護的三層式應用系統：前端、後端 API、資料庫。它不是一支可以直接執行的工具，也不是操作 SOP——文件本身在開頭就明確自我定位為「純文件（系統架構規劃），無程式碼」。換句話說，這是設計圖，不是房子。

## 為什麼值得關注

過去幾週收錄過不少單點腳本：`get_bmc_bios_info`、`IPMI_code_for_Fan_code`、`終端機即時監看`（NIC/RDMA 監控）、`BIOS_and_BMC獨立通道`，每一支都解決「怎麼從 BMC/IPMI/Redfish 撈出某一種特定數據」的問題。這份架構圖回答的是下一層的問題：如果要把這些零散的讀取腳本，整合成一個有 Web UI、有資料庫、有權限控管的正式監控平台，該怎麼切模組、選技術棧？這正是「寫了很多工具腳本之後」常見的下一步——不再滿足於單次執行的 shell script，而是想要一個隨時能打開看即時狀態的儀表板。

## 技術重點

架構圖把系統切成三層，每層都給出具體技術選型，不是空泛的「前端／後端／資料庫」三個字：

- **前端**：Svelte（文件裡誤植為 Zeu.js，應為 Vue.js 的筆誤）+ HTML/CSS/JS，搭配 Chart.js 畫感測器趨勢圖，UI 用 Summary / System Board / Sensor 三個分頁組織資訊，並規劃了 Refresh / New / Delete 等操作按鈕模組，以及 BMC IP / BMC ZIP 的展開區塊。
- **後端**：Python FastAPI 或 Java Spring Boot 二選一，核心職責是對接 IPMI / Redfish / SNMP 三種協定把資料撈進來，轉成 JSON 供前端消費，並用 JWT / OAuth2 做身分驗證——這代表這套系統預期是多人共用、需要權限分級的維運平台，不是個人單機小工具。
- **資料庫**：MySQL 或 MSSQL，規劃了系統資訊表（CPU/Memory/PSU/HDD）、感測器紀錄表（溫度、電源狀態、時間戳記）、使用者權限表、操作紀錄表——等於把「每次讀出來的感測器數值」都要留歷史軌跡，而不只是看當下一次的快照。
- **部署建議**給了兩條路：桌面工具用 PyInstaller 打包成單一執行檔（貼近目前團隊習慣直接丟一支腳本去跑），或是做成 Web Widget 部署在伺服器上長期常駐——兩個選項分別對應「輕量驗證」跟「正式維運平台」兩種使用情境。

## 可延伸應用角度

這份內容最適合做成「架構設計」或「系統規劃」類型的影片，而不是工具教學——重點不是演示怎麼跑，而是講清楚「為什麼這樣切模組」「三層架構各自負責什麼」。可以跟系列裡已經收錄的 BMC/IPMI/Redfish 相關工具（`get_bmc_bios_info`、`IPMI_code_for_Fan_code`、`BIOS_and_BMC獨立通道`、`sit-master-toolkit-unified-command-center`）做對照剪輯：先讓觀眾看過一支支獨立腳本在解決什麼問題，再用這張架構圖收尾，說明「這些腳本背後，其實可以長成這樣一套完整系統」，形成一集「從腳本到平台」的系列總結影片。
