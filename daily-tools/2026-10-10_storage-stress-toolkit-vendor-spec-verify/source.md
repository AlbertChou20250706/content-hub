SIT Storage All-Stress Toolkit 的 `--spec-verify`（Layer 3）是一套把 NVMe SSD 的實測效能，拿去跟廠商官方規格書逐項對帳的驗證機制——不是再加一組壓測參數，而是一條「怎麼量才算公平比對」的方法論,從前處理怎麼做、穩態怎麼判定、到規格數字從哪裡來、誰有權寫進資料庫,每一步都寫死成可重複執行的流程。

> 來源路徑：`FIO_Test/For_RedHat/v9.21.0/`（`Storage_Stress_AlbertStyle_Linux.sh` v9.21.0，含 `run_spec_verify.sh`、`drive_specs.conf`、`spec_lookup_prompt.md`）
> 這支腳本本體（PCIe 降級判定、溫度監看）已經在 2026-08-19 的《SIT Storage All-Stress Toolkit》裡介紹過；這篇只聚焦在那篇完全沒提到的新增主題：Layer 3 規格書比對子系統。

## 為什麼值得關注

硬體驗證裡最常被忽略的一步,不是「怎麼測」,而是「測出來的數字,憑什麼跟規格書比」。多數人直接拿一次性的 fio 快照去對規格書的 IOPS 數字,但企業級 SSD 的隨機寫入規格,幾乎都是「打滿容量、GC 進入穩態之後」才量得到的持續值——空碟直測往往比規格書高出兩三倍,不是碟子超標,是量測時機不對。這套工具把「怎麼量才公平」這個容易被跳過的方法論問題,變成一段可重複執行、有版本歷史的程式碼,而且連「規格數字從哪裡來」這個人為環節都設計了防呆。

## 技術重點

實際下載並讀過 `For_RedHat/v9.21.0/` 底下的 README、主腳本、`run_spec_verify.sh`、`drive_specs.conf`、`spec_lookup_prompt.md` 之後,幾個真正值得拆解的設計:

- **四項固定量測對應廠商量測條件**:循序讀/寫固定用 128k、QD32;隨機讀/寫固定用 4k、QD512(欄位名分別對應 `drive_specs.conf` 的 `seq_read_mbs`/`seq_write_mbs`/`rand_read_kiops`/`rand_write_kiops`)。這組參數不是隨意選的,是照著廠商規格書的量測條件反推回去,否則同一顆碟换個 QD 就能測出差一倍的數字,比對毫無意義。
- **穩態前處理的兩種收斂判定**:隨機寫入要先跑 `SPEC_PRECOND_ROUND_SEC`(預設 600 秒)一輪一輪地測,直到判定進入穩態。平坦收斂很直覺(連續 3 輪數字差在 10% 內);但 v9.15.0 新增的**週期性收斂**才是真正的技術亮點——部分碟的穩態其實是固定週期的忽高忽低震盪(GC 循環造成),不會真正「平」下來,於是原本「連續 3 輪平坦」的判定永遠不會觸發,整批碟會一路跑到 `SPEC_PRECOND_MAX_SEC` 上限卻仍判定未收斂。`spec_check_periodic()` 這段(讀自腳本第 2702-2739 行)試週期 2 到 `SPEC_PERIODIC_MAX_PERIOD`(預設 4),把歷史輪數依「輪數 mod 週期」分組,只要每組最近兩個同相位的值,差距在 `SPEC_PRECOND_VARIANCE_PCT`(預設 10%)容許範圍內,就判定該週期收斂:
  ```bash
  spec_check_periodic() {
      local vals=("$@")
      local n="${#vals[@]}"
      local max_period="${SPEC_PERIODIC_MAX_PERIOD:-4}"
      for ((p = 2; p <= max_period; p++)); do
          local need=$((p * 2))
          [ "$n" -lt "$need" ] && continue
          # ...把最近 need 輪依 (i-start) % p 分組,比對同相位最近兩個值的差距...
          if ! awk -v r="$grange" -v m="$gmean" -v t="$SPEC_PRECOND_VARIANCE_PCT" \
              'BEGIN{ pc=r/m*100; exit !(pc<=t) }'; then
              ok=0; break
          fi
      done
  }
  ```
  實機用同一款碟(KCD9DPUG3T84)三顆不同實體碟、六次重複測試,全部在第 6 輪一致判定週期 2 收斂——不是單次僥倖,是可重現的規律。
- **收斂之後還要跑夠多週期才敢回報**:偵測到週期性收斂只是第一步,真正量測時還要延長覆蓋 `SPEC_PERIODIC_CYCLES` 個完整週期,這個預設值從 v9.17.0 的 2,一路經 v9.18.0(→4)、v9.19.0(→8)、v9.21.0(→16)不斷往上調,每次調整都有實機數據佐證——未收斂快照比規格高 207%,1 週期縮到 +74.4%,2 週期 +43.4%,4 週期 +25.3%,8 週期 +16.6%,但縮小比例從 58% 放緩到 65%,意味著這條曲線不是收斂到規格值,而是收斂到某個比規格值高一截的平台——README 直接把這個落差歸因於方法論落差,而不是硬碟有問題:KIOXIA 官方的兩份文件都沒有揭露測試用的佇列深度或前處理方法,所以不管怎麼調週期數,都無法保證最終追上規格書的確切數字。
- **一次失敗的假設,被 A/B 測試明確推翻**:v9.20.0 聽說 KIOXIA 原廠自己的驗證流程要跑 8-12 小時,直接把前處理時間下限/上限從 1800/10800 秒拉長到 28800/36000 秒(8/10 小時),賭的是「前處理不夠久才是落差的原因」。結果 v9.21.0 在同一顆實體碟上做 A/B 對照——1 小時前處理量到 373K(+16.6%),8 小時前處理量到 372K(+16.2%),幾乎沒有差異,直接證明這個假設是錯的,於是把前處理時間改回原值,把力氣轉而投入週期數。這是一段完整記錄在 CHANGELOG 裡的「提出假設→實測驗證→推翻→調整方向」過程,不是事後包裝的敘事。
- **規格數字從哪裡來,被設計成「AI 查、人核對」的兩段式流程**:`drive_specs.conf` 裡每一款碟的規格值不是憑空填的,`spec_lookup_prompt.md` 是一段設計給另一個「具備網頁搜尋能力的 session」貼上去用的 prompt,裡面寫死一串反幻覺規則——只採信官方產品頁/官方 PDF/官方新聞稿;查無資料要明確回「NOT FOUND」,不准拿同系列其他容量的數字去推算;不同官方文件數字不一致時兩個都列出來,不准自己選一個;typical/max/sustained 三種數值必須分開標註,不能混用。查完的結果故意設計成**不能讓那個 session 自動寫進 `drive_specs.conf`**,必須由人工核對來源網址是官方網域之後手動貼上——README 原話是「規格數字是判定基準，錯一個字就可能誤判整批碟,人工過目是最後一道防線」。
- **一個操作員會犯的錯,被寫成一支不重複任何邏輯的包裝腳本**:`--spec-verify` 這個模式忘了帶旗標,或忘了帶 `-y`,腳本會直接退回成一般破壞性壓測——這個操作失誤在實機上真的發生過兩次(2026-08-19/20)。`run_spec_verify.sh` 的解法很乾淨:不複製主腳本任何掃描/選單/安全邏輯,純粹 `exec "$MAIN_SCRIPT" --spec-verify "$@"`,只固定住這一個旗標,其餘全部原樣轉呼叫,代表主腳本改版時這支包裝腳本幾乎不用跟著改。

## 可延伸應用角度

- 適合做成「怎麼幫壓測工具加上規格書比對」系列影片的核心案例,重點不是示範 fio 怎麼用,而是示範「公平比對」這個方法論問題怎麼拆解成前處理收斂判定、多週期取樣、規格來源治理三個子問題分別解決。
- 週期性收斂偵測與 v9.20→v9.21 的 A/B 測試推翻假設這兩段,可以剪成獨立的「用實機數據驗證、推翻自己假設」短片,呈現這套工具不是寫完就定型,而是持續有真實硬體在驗證參數選得對不對。
- `spec_lookup_prompt.md` 的「AI 查、人核對、不給寫檔權限」設計,可以延伸到任何「需要高信度外部資料、但來源可能有雜訊」的場景,作為「AI 輔助研究 + 人工守門」協作模式的具體範例,而不是空談 AI 治理原則。
