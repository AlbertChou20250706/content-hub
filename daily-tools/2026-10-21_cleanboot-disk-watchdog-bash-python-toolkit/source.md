`Cleanboot` 是一套根目錄（`/`）空間看門狗與自動清理工具，同一個問題被 Albert 用兩種語言各寫了一套：Linux Bash 版（v1.1 一路演進到 v1.5）鎖定通用發行版，Python 版（v1.6）則專攻 RHEL 系（RHEL／AlmaLinux／Rocky／Oracle Linux），兩者都會在根目錄使用率逼近門檻時自動清理 `/tmp`、`/var/log`、`/var/cache`，寫出 HTML 報告，並能裝成開機＋每小時執行的 systemd timer。

## 為什麼值得關注

SIT 測試機台長時間跑測試，log 與 core dump 很容易把根目錄撐爆，而磁碟一旦打滿，後續測試會莫名失敗、連 SSH 都登不進去——這是測試現場很熟悉、但往往要等到出事才想起來處理的坑。這套工具把「定期檢查 `/` 使用率、超過門檻就清垃圾」這件事從人工巡機變成自動化背景服務，而且從資料夾裡 v1.1 → v1.2 → v3 → v1.4／v1.4.1 → v1.5（Bash）再到 v1.6（Python）的版本軌跡可以看到，這不是寫完就丟著不管的腳本，是持續被使用、持續被修的工具——包括換語言重寫這種大動作。

## 技術重點

實際下載並讀過 `Linux/Bash/`、`Linux/Python/` 兩份 README 與腳本說明後：

- **兩個版本的「門檻」語意完全相反，是個很真實的踩坑案例**：Bash v1.5 的 `--threshold`（預設 25）代表「使用率 ≥ 門檻就清理」；Python v1.6 的 `--threshold`（同樣預設 25）卻代表「保留的安全餘裕」,實際上要「使用率 > 100 − 25 ＝ 75%」才會動作。同一個參數名字、同一個預設值 25，兩個版本的實際觸發點天差地遠（25% vs 75%），如果照搬一邊的操作習慣去用另一邊，很容易抓錯清理時機。
- **Bash v1.5 用 `lsof -nP +L1` 抓「已刪除但仍被行程占用」的檔案**：這類檔案 `rm` 不會真的釋放空間（行程還開著 fd），清理腳本偵測到後會在報告裡標示出來，建議使用者重啟對應行程——這是很多人清磁碟空間清半天沒有效果時會忽略的細節。
- **Bash v1.5 預設會停用並停止 `kdump` 服務**（沿用 v1.1 行為），要保留 kdump 得明確加 `--no-kdump`；這代表清理腳本的預設行為本身帶有副作用，不是單純的「刪檔案」。
- **Python v1.6 預設是乾跑（dry-run），要真的清理得自己加 `--yes`，但 `--install-systemd` 裝成的開機＋每小時 timer 卻會直接以 `--yes --aggressive` 執行**——`--aggressive` 包含 `dnf clean all`、`autoremove`、只留最新 2 個核心、清 coredump，以及 `docker/podman system prune -af --volumes`（會真的刪掉未使用的容器磁碟區）。也就是「手動執行很安全（預設不動手）」跟「裝成自動服務後其實預設最激進」是兩種完全不同的風險等級，安裝前得先確認機器上沒有要保留的舊核心或未用容器資料。
- **Python 版額外動到 `journald.conf`**：把 `SystemMaxUse` 寫成 200M 並重啟 `systemd-journald`，屬於會改系統設定檔的操作，跟單純刪暫存檔不是同一個風險層級。
- 同一個 `Linux/` 目錄下還並存著 `Cleanboot by v1.4/`（含獨立安裝/移除腳本）、`Mitaccomputing/Cleanboot by v1.5/`（另一份內容不同的 v1.5，約 8KB）、`Old/`（v1.1～v3 的安裝包），是觀察一個工具在同一個人手上怎麼反覆改版、甚至同版本號分裂出不同內容的少見活標本。

## 可延伸應用角度

- 這支工具剛好是先前已發布的 Suno 歌曲〈看門狗〉（`suno-song-prompt-watchdog-disk-cleanup`）背後真正的腳本原型——歌詞裡的 `lsof`、`--dry-run`、「每小時繞一圈」的 systemd timer 都對得上 Bash v1.5 的實際行為,適合做成「聽歌解密：這首歌到底在講哪支腳本」的技術頻道影片，跟音樂頻道內容互相導流。
- 「同一個參數名字、同一個預設值,兩個語言版本的實際語意完全相反」這個案例很適合剪成一支排錯／踩坑短片，提醒工程師換版本、換語言重寫時,別只看參數名字就假設行為一樣。
- `--install-systemd` 預設帶 `--aggressive` 這種「手動安全、自動化後變激進」的設計落差，可以延伸討論自動化腳本的 safe-by-default 設計原則，適合搭配其他 SIT 自動化系列（例如 Configure_kdump_halt）做成一集談「自動化到底該多保守」的內容。
