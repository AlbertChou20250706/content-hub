Refish_DMTF 是一套把 DMTF 官方的四組 Redfish 開源驗證工具（Service Validator、Protocol Validator、Interop Validator、Tacklebox）包裝成 15 支分階段腳本的 BMC 合規測試環境，從一台 Client 對受測伺服器（SUT）的 BMC 跑完整的 Redfish 介面一致性檢查，不需要在 SUT 上安裝任何東西。這是先前已發布過的 `_Redfish_Test`（交接文件與雙語報告那條線）的另一條線——同一個 B8056 專案的 Round 2（新韌體 BMC v0.05／BIOS V3.05），但這次的素材是實際跑測試的腳本本體，不是報告彙整。

## 為什麼值得關注

BMC 的 Redfish 合規測試有一個天生的矛盾：DMTF 官方工具本身只管「發一個請求、比對 schema」，但其中有些 TC 會建立帳號、鎖定帳號、清空 EventLog、重開機、動 BIOS 屬性——這些操作一旦做錯或中斷在一半，很容易把受測系統留在一個不乾淨的狀態。Refish_DMTF 的做法不是直接把官方工具的 CLI 甩給使用者，而是用 15 支腳本把風險分級、把「會不會動到 BMC/SUT」這件事變成腳本設計的第一原則：階段 1（唯讀檢查）、階段 2（低風險暫時性變更）、階段 3（電源與開機）、階段 4（改動 BMC 設定）層層往上加風險，且每一層都承諾中斷也會自動還原。這種「先分級、再自動化」的順序，對任何要把官方／第三方的驗證工具接到自己流程裡的人都是值得參考的設計思路，而不只是「怎麼裝 Redfish 驗證工具」的教學。

## 技術重點

讀過 README 與 `step13_tacklebox_phase2.sh`、`step14_tacklebox_phase3_power.sh` 等腳本後，幾個具體設計：

- **每個風險等級都有自己的「自動還原」保證**：階段 2（`step13`）的 `tc306` 建立 4 個暫時帳號、改密碼、改角色、停用／啟用，測完全部刪除；`tc306lock` 更進一步要求人在 WebUI 手動改鎖定政策、連續輸錯密碼 3 次、解鎖後再登入，腳本負責呼叫 `rf_accounts.py -unlock`，最後把鎖定政策**改回原值**並刪除帳號。腳本標頭明確寫出「結束時一定還原，中斷時也會還原」，而不是只在正常路徑下才清理。
- **用 BMC 的「已讀成員但讀不到」這種異常繞過官方工具的 bug**：這台 BMC 的帳號集合會列出一個成員（例如 `Accounts/50`）但實際讀取回 404，Tacklebox 官方工具逐一讀取時會直接丟 `KeyError: 'UserName'` 當掉。腳本的做法是把這個成員標成 `DANGLING`、印出說明後繼續執行，真正的登入失敗（401/403）才會在測試前中止——也就是先分辨「這是 BMC 的已知怪癖」還是「這是真的測試失敗」，而不是讓第三方工具的例外直接中止整個流程。
- **互動輸入從「打字」收斂成「選字母」**：v1.8（2026-11-03）把所有提示從輸入文字或數字改成單一字母選項（a/b/c…），只有 IP、帳號、密碼仍需要打字；需要人眼確認的題目額外標記 `[MANUAL OBSERVATION]`，觀察不到時可以選 `z` 記錄成「需要人工觀察」，而不是卡住整支腳本等人輸入自由格式文字。
- **一次性開機（TC302）與 BIOS 還原（TC304）都寫成「可換機型」而非寫死這台的參數**：`step14` 把 BIOS 屬性名稱對照（例如這台把 `Always On` 顯示成 `Previous`）、要略過比較的易變屬性（開機時間戳記）、系統資源路徑（`Systems/Self` vs `Systems/system`）全部改成環境變數可覆寫，README 第 9 節直接列出換到另一台（例如 8261）時要改哪幾個環境變數，而不用動腳本本體。
- **腳本標頭即變更紀錄**：每支 `step*.sh` 開頭都固定格式記錄「設計者（Albert Chou + Claude Code）、版本、對象、逐版變更」，15 支腳本從 v1.0 到 v2.0 的修法歷程完整可追，對照 README 第 8 章的「常見問題」表（HTTP 400/428/503 各自對應哪種 BMC 行為、該怎麼處理）可以看出這套工具是在真機上反覆踩坑、逐步補強例外處理長出來的，不是一次性寫完的腳本。

## 可延伸應用角度

- 可以跟已發布的「Redfish 交接雙語報告」那篇做成系列對照：那篇講「怎麼把測試結果變成看得懂、交接得動的報告」，這篇可以講「怎麼把官方驗證工具包裝成分風險等級、會自動還原的測試腳本」——同一個專案的兩個互補角度。
- 「分風險等級自動化＋承諾還原」這個設計模式本身值得抽出來做一段科普，可以對照其他動 BIOS／BMC 的工具（例如之前介紹過的 BMC_Fan_SKU_Tool、get_bmc_bios_info）討論「會改動硬體狀態的自動化腳本該怎麼設計安全網」。
- `DANGLING` 成員繞過與字母選單互動這兩個小技巧，適合剪成「跟第三方驗證工具合作時怎麼處理它的已知 bug」短篇，呼應正在做的 BMC/Redfish 系列內容。
