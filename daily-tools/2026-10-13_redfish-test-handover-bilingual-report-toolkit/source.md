_Redfish_Test 是一套累積 B8056（AMD SP7）BMC（AMI Redfish Server、BMC 4.06.0）Redfish API 測試的文件、報表與交接工具組，把 TC295–TC309（14 個 TC、200 個步驟）的執行紀錄整理成雙語（繁中／EN 可切換）HTML 報告，並用一份交接指南統一團隊的架設、執行、回報與換專案方式。

## 為什麼值得關注

Redfish 這類 BMC API 測試,案子一多很容易卡在「人走了、知識也走了」的問題——哪個 TC 測過、測到哪一步、證據放在哪、換一台機器要改什麼,全靠記憶或零散筆記,交接給下一個人常常要重新摸索一輪。這份資料夾的做法是把「交接」當成第一優先:先寫一份涵蓋架設、每個 TC 怎麼跑、報告怎麼更新、安全規則、不同 BMC 版本差異、常見問題、換專案做法的交接指南,再搭配可雙語切換、看得到「做到哪裡／結果／證據在哪」的報告,而不是只留下一堆原始 log。對任何需要長期維護、人員會流動的測試專案,這種「文件先於工具」的交接設計思路比工具本身更值得參考。

## 技術重點

實際讀過 README 後,幾個值得注意的設計:

- **報告產生是自動彙整、不是手動貼結果**:`02_Report/update_report.bat` 會自動讀取 `results_*.txt`、`summary.txt`,以及 Protocol Validator 產出的 `results.json`（對應 TC295）,彙整成 `report_data.js` 驅動的 HTML 報告,執行者只需要把 Client 端跑出來的時間戳記資料夾複製進 `02_Report/Logs/<步驟>/`,雙擊 `.bat` 即可更新,不需要手動排版或拼接。
- **三個角色故意分離,降低誤操作風險**:伺服器只用來放檔案,不在上面執行任何東西；測試腳本在 Client（RHEL 10.2）執行；報告更新在自己的本機做。README 特別強調報告連結是**相對路徑**,必須複製整個 `_Redfish_Test` 資料夾（不能只複製 `02_Report`）才能正常開啟,這是容易被忽略但一旦漏做就會讓報告全部連結失效的細節。
- **會動到 BMC/SUT 的操作都有一道確認關卡**:凡是可能改動 BMC 或受測系統（SUT）狀態的腳本,執行前都會先印警告並要求輸入 `yes` 才會繼續;帳號密碼在執行當下輸入、不寫進任何檔案,所有紀錄裡殘留的暫時密碼也都已遮蔽——對一份會被多人、跨專案重複使用的測試工具,這種「預設安全」的態度比功能本身更值得學。
- **換機器不用改腳本**:每支腳本一開始會詢問 BMC IP 與 SUT IP,直接按 Enter 可套用預設值,把「環境參數」跟「測試邏輯」分開,減少換機型、換團隊使用時誤改程式碼的風險。
- **進度用三態以上的狀態表追蹤,而不是單純的二元通過／失敗**:目前 14 個 TC 分成「通過」「有發現（已寫 Jira 草稿）」「部分執行」「尚未執行」四種狀態,發現的問題先轉成英文 Jira 草稿存底（尚未送出）,讓測試進度跟問題追蹤的狀態都保持透明,不是測完才一次性整理。

## 可延伸應用角度

- 適合做成「交接文件怎麼寫才真的有用」的案例:這份交接指南覆蓋架設、逐 TC 操作、報告更新、安全規則、版本差異、常見問題、換專案 SOP 七個維度,可以直接拿來對比一般工程團隊常見的「只留一份簡短 README」交接方式有什麼落差。
- 自動彙整多種 log 格式（`results_*.txt`、`summary.txt`、`results.json`）成單一雙語報告的做法,可以延伸講「測試報告自動化」這個主題,跟之前介紹過的 BMC／IPMI 系列工具放在一起做對照。
- 「伺服器只放檔案、本機才執行」的角色切分與操作前二次確認機制,適合做成一段簡短的測試環境安全設計科普,呼應先前 OOB_Check 介紹裡提到的密碼安全處理手法。
